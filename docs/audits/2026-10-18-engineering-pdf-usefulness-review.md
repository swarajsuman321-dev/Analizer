# Review of the app-generated Engineering report.pdf

Reviewed 18 October 2026. Repository: swarajsuman321-dev/Analizer. This assessment reviews the supplied PDF, generated by Appliance Signal Studio **2.3.1**; it does not replace the underlying engineering measurements or implement application changes.

## Is this report useful?

**It has limited value as a diagnostic export, but it is not ready to support an engineering acceptance or product-performance decision.** It identifies the source recording, preserves a source fingerprint, shows two useful traces and distinguishes unavailable results from evaluated acceptance. Those are good foundations. The export currently makes the engineer search thousands of pages to discover that most expected results could not be calculated and that some channel meanings need review.

The most important changes are to expose data/mapping readiness before results, summarize recurring events, and turn the PDF into a short engineering narrative with a separate complete evidence export. A shorter report alone will not fix incorrect channel roles or unsupported calculations.

## What is worth keeping

- Source-file SHA-256, application/profile versions and report generation time.
- Explicit Not Available and Not Evaluated states. Missing inputs must never become fabricated results or automatic passes.
- The distinction between deviation colors and configured acceptance limits.
- Time axes in minutes, unit labels and source channel names on plots.
- Preservation of detailed records for later investigation, provided those records move to a suitable complete evidence export.
- The explicit qualification “Cycle duration (recorded span)”. Keep that qualification: a file's first-to-last timestamp is not necessarily the actual program start-to-finish duration.

## Priority 0 — correct interpretation and show readiness

### 1. Review actual speed versus speed command

Page 4040 maps `Drump Speed` to canonical `speed` by profile alias, while `Drump speed feedback` is **unmapped**. Page 1 then calls the result “Peak drum speed” and reports 1200 RPM.

The PDF does not establish that `Drump Speed` is a measured feedback channel. Treat 1200 RPM as the peak of the selected source until its meaning is confirmed. Do not automatically replace one channel with another just because its name sounds plausible.

**Required change:** separate target/command speed and actual/feedback speed in mapping review and reporting. Show canonical role, selected source, declared/confirmed unit, mapping method and review status beside each affected KPI. Where multiple plausible sources exist, ask for a mapping decision and suppress an unqualified “actual speed” result until reviewed. After confirmation, report target speed, actual speed, tracking error and spin stability separately.

**Verification:** a file containing both command and feedback cannot silently produce an actual-speed KPI from the command channel. Explicit overrides persist and remain visible in exports.

### 2. Explain missing results and resolve unit conflicts

The mapping page recognizes `Current Temperature` but leaves its source unit blank. A late quality note says there is no verified conversion from unitless to °C. This means peak temperature is **blocked by unit verification**, which is different from “no temperature sensor recorded”. Similarly, `vbus` and `Wash Stage` have unverified units. The current PDF conceals these practical distinctions behind repeated Not Available labels.

Both `Water Pressure pulse time` (µs) and `water pressure` (Pa) map to canonical `water_pressure`. A pulse-time measurement must not be treated as pressure without a verified calibration; ambiguous canonical mappings must be reported directly.

**Required change:** add a short readiness table before KPI results:

| Desired result | Current blocker | Engineer's next action |
|---|---|---|
| Energy and power | Only an RD recording is identified; no active-power source established | Add the matching power recording, verify units and alignment, or explicitly select machine-only scope |
| Temperature results | Temperature recognized, source unit unverified | Confirm the logger's unit from its specification or calibration; save that confirmation |
| Pressure results | Two different measurement types claim one canonical role | Select the direct pressure source or configure a verified pulse-to-pressure calibration |
| OOB retry count | `oob_retry_times` is unmapped | Confirm counter meaning and units; review reset handling |
| Phases | No supported phase interpretation established | Verify stage-code units, code meanings, boundary rules and timing coverage |
| Acceptance | Limits not configured | Enter the applicable test-plan limits and their revision/source |

Do not infer °C, Pa, stage codes or acceptance criteria solely from a filename or familiar column name. Preserve physical units, provenance and calibration evidence.

**Verification:** every important unavailable KPI has a specific reason and corrective action; missing source, ambiguous mapping, unverified unit, insufficient coverage, unsupported phase and unconfigured rule remain distinct states.

### 3. Put timing coverage beside every timing-dependent result

A reproduction using the repository recording with the **same source hash as the PDF** found:

- 1,005 duplicate timestamps in each of the mapped speed/valve/drain channels.
- Median positive sample interval approximately **0.149 seconds** after duplicate resolution.
- Automatic gap limit approximately **0.447 seconds**: three times that median.
- Supported elapsed-time coverage approximately **43.84%** for the reproduced speed, inlet-valve and drain traces.
- The same **10,195 speed-dropout detections** seen in the PDF.

This reproduction used inspected source commit `1d8d54c96ed2aa10c1d159b6895224dee751787b` (2.3.2), rather than the exact generating executable. The counts and displayed KPI values agree with the uploaded 2.3.1 report. It explains the observed behavior but does not independently establish whether the logger's longer intervals represent lost samples or its intended acquisition schedule.

The summary gives cold-inlet active duration **1.50082 min** and drain active duration **0.449533 min** with a duplicate-timestamp warning, but does not show the much more consequential supported-time percentage.

**Required change:** show observed span, supported duration, coverage %, duplicate count, missing values, gap threshold and timing policy. Label these active durations as **supported-time totals**, not complete-cycle totals. A peak observed sample and a complete time-integrated quantity need different adequacy rules. Do not invent a universal coverage pass threshold: define it in the test plan.

**Verification:** removing supported samples reduces reported coverage; no missing interval is silently counted as known ON/OFF time, energy or water. The PDF and Excel agree on coverage and interval policy.

### 4. Separate acquisition quality from appliance faults

The detected rows describe sampling gaps, not demonstrated washing-machine failures. Many example gaps are around half a second to one second. The rule's name and “Detected” status must not turn these into 10,195 asserted motor faults.

**Required change:** separate Data Quality, Rule Evaluation Status and Appliance Events. Report the effective gap rule and sampling assumptions, review irregular/multirate acquisition behavior, and disclose sensitivity to any configured threshold. Threshold changes must not erase or interpolate raw measurements. Show a few representative gaps and a timeline overview; use a complete machine-readable log for all records.

**Verification:** a channel absent from the recording is Not Evaluated, not a detected dropout; known irregular acquisition is handled under an explicit policy; actual device faults require independent configured evidence.

## Priority 1 — make the document usable

### 5. Replace thousands of pages with event summaries

The inspected renderer converts tables with more than seven columns into `Record / Field / Value` rows. It then wraps every field and emits pages of 28 rendered rows. Repeating rule definitions and JSON per event expands roughly 10,000 records into 4,020 PDF pages. This is a presentation design problem, not a reason to delete events from the evidence.

**Required change:** use a compact summary such as:

| Class | Channel/rule | Count | Effective threshold | Total affected time | Longest interval | First/last time | Evidence |
|---|---|---:|---|---|---|---|---|
| Data quality | Selected speed source / gap rule | 10,195 | 0.447 s in reproduction | Calculate from interval union | Calculate | Calculate | Complete event log |

Values not calculated in this review are deliberately not invented. Keep event time, duration, severity and source together in one row. List only representative or highest-priority events in the default PDF and state precisely how many were omitted there. Preserve every raw event in Excel/CSV, including individual IDs and the grouping rule. Merge adjacent alerts only in an explicitly labelled summary view, never by silently changing the original event evidence.

**Verification:** this fixture generates a default report of a defined, bounded size—suggested design target **8–12 pages**, with the final budget agreed by report scope—while the detailed export retains all 10,231 log records. Increasing event count does not increase default PDF length without an explicit appendix choice. Report previews show expected pages before export; generation remains cancellable.

### 6. Give the engineer an answer on page 1

Use a visible status such as **Incomplete analysis — mapping, timing coverage and acceptance setup require review**. State which questions can and cannot be answered, the top three blockers, and the next actions. Separate “Analysis complete”, “Data adequate” and “Acceptance evaluated”; they are different conclusions.

Manufacturer, model, scenario and boundary conditions are missing in this report. Add reviewed test ID, operator, program/settings, intended load, ambient/inlet conditions, instrumentation/calibration and acceptance-plan revision where relevant. A 4 kg filename is not a verified load entry, and “IEC” in a filename does not establish a particular IEC procedure or compliance result.

### 7. Make graphs explain the test

Page 18 provides a useful whole-recording overview, but it shows just two traces. It has cursor lines without numeric A/B values, interval scope or a result table, uses a pale pressure trace, and the lower axis label/footer compete for space. The plot does not make the reproduced unsupported-time coverage obvious.

**Required change:** show the selected source role and mapping status, applicable phases, supported versus unsupported spans, data-quality shading and event references. Add a spin-region detail view and, when verified, temperature/heater and valve/pressure relationships. Include A/B timestamps and an interval summary only if cursors have a defined role in the report. Use readable print-safe colors and reserve a footer margin. Define whether the PDF shows the whole run, the active cursor interval, or both; align KPI scope with that choice.

Do not add unsupported phases, fabricate missing temperature/power curves, or connect missing measurements as though coverage were known.

### 8. Move raw configuration to the companion evidence package

Pages 4–16 contain configuration JSON; pages 4041–4049 contain calculation definitions mostly in JSON form. Retain one short traceability section with source filename, hash, app/profile version, mapping review, calibration references and acceptance-plan ID. Move full configuration and recipes to Excel/JSON. Explain formulas in engineering language with units, integration policy and quality requirements.

Add page numbers, contents/bookmarks, consistent human-readable timestamps and a report identifier shared with the companion files. Use source basenames by default in shareable output; absolute local paths in PDF metadata can reveal workstation/user-directory information without adding engineering value.

## Proposed default report

| Page budget | Content |
|---|---|
| 1 | Purpose, test identity, scope, overall readiness, usable primary results and top blockers |
| 2 | Source roles, mapping/unit review, calibration and data-quality coverage |
| 3–4 | Phase/timeline overview and verified speed/temperature/pressure/power plots as available |
| 5–6 | KPIs with units, source, scope, quality/coverage and configured acceptance |
| 7–8 | Grouped events, selected evidence/detail plots, conclusions and actions |
| 9–12 if needed | Traceability, concise calculation methods and approved additional evidence |

Unavailable mandatory results remain visible with reasons. Optional unconfigured features can move to a compact readiness list. Detailed export: all KPI results/reasons, every event, full mappings, configuration, source fingerprints and calculation definitions. A page target is a product requirement to agree, not a requirement to discard evidence or shrink text until it is unreadable.

## Recommended implementation order

1. Add report readiness and coverage summaries; review command/feedback roles, pressure conflicts and unit confirmation.
2. Replace vertical event expansion with grouped PDF summaries plus complete detailed export.
3. Separate acquisition-quality alerts from device faults and clarify gap-threshold policy.
4. Add a report scope, source-role and expected-length preview; fix plot margins, annotations and readable colors.
5. Simplify metadata/definitions, add navigation and verify PDF/Excel numerical agreement.

The important regression fixture is this actual 4,049-page input case. Validate missing-source and conflicting-mapping states, command versus feedback, duplicate/irregular timestamps, unknown units, no acceptance limits, event-count preservation, bounded default PDF length and plot/footer separation. Do not validate the redesign only with clean synthetic channels.

## What you can safely use from this report now

Use it to establish **which recording/profile/app version was exported**, inspect the selected speed and pressure traces, and identify gaps in configuration and acquisition quality. Treat **265.021 minutes as recorded span**. Treat **1200 RPM as the peak of the presently mapped source**, pending confirmation of actual feedback. Do not use this PDF alone to approve energy/water consumption, temperature performance, complete valve timing, phase durations, fault-free behavior or acceptance compliance.

All 4,049 pages were text-extracted and counted by section. Representative cover, chart and anomaly pages were visually inspected; this is not a manual reading of every repeated event page. Log records/statuses were counted from extracted rows. Mapping and limitation pages were inspected directly.
